# AIエージェントプラットフォーム アーキテクチャ（rev.3）

2026-09 / 対象: 社内業務の自動化＋Webサービス開発。オープンソースベース、社内利用のみ（製品化しない）。

---

## 1. 構成の全体像

### ハードウェアと役割

| 要素 | 役割 |
|---|---|
| **本番 AWS**（cetacea.jp） | コンテンツ・Webサービスの提供先。WordPress / Webサービス / Postfix。Mac miniからは**読み取りのみ** |
| **Mac mini M6 / 32GB**（自宅・常時稼働） | 開発ホスト ＋ 業務機 ＋ 常駐エージェント の3役 |
| **MacBook** | 持ち出し用の端末。Tailscale経由でMac miniに接続。作業実体はMac mini側 |
| **CI**（GitHub Actions等） | 本番の資格情報を持つ唯一の場所。Git push を受けてデプロイ |

### 3つのゾーン

- **ゾーン1 — 本番（AWS）**: 提供先。変更はGit → CI経由に限る。外形監視の実行元も兼ねる
- **ゾーン2 — 開発（Mac mini）**: コード生成・ビルド・テスト・コンテンツ制作。成果物は `git push` まで。顧客データには触れない
- **ゾーン3 — 業務（Mac mini）**: 請求・契約・顧客対応・文書。区分Aのデータを保持。本番にもGitにも触れない

### データの流れ

```
MacBook ──Tailscale──▶ Mac mini
                        ├─ 業務ゾーン ─┐
                        ├─ 開発ゾーン ─┤
                        │              ▼
                        │        共通基盤（LiteLLM / MCP / PostgreSQL / Phoenix）
                        │              ▼
                        │        送出ゲート（マスキング・記録）──▶ 商用LLM API
                        └─ git push ──▶ Git ──▶ CI ──▶ 本番AWS
```

外部への出口は**送出ゲート経由の商用API**と**git push**の2本だけ。本番への書き込みはCIのみ。

## 2. 決定的な制約 — 32GBのメモリ配分

Mac mini M6 はユニファイドメモリ **最大32GB**、帯域 **153〜170GB/s**（64GB / 307GB/s は M5 Pro 構成のみ）。CPUとGPUでメモリを共有するため、これが全ての上限を決める。

**常駐（13GB・常に載っている）**

| 用途 | GB |
|---|---|
| macOS ＋ 常駐 | 6.0 |
| データ層（PostgreSQL / Redis） | 2.5 |
| エージェント層（LangGraph / LiteLLM / MCP / Phoenix） | 3.5 |
| 検出パイプライン（正規表現 + CPU NER） | 1.0 |

**残り19GBをモードで奪い合う**

| 開発モード（日中） | GB | | 業務モード（夜間・機密処理） | GB |
|---|---|---|---|---|
| Node・ビルド | 6.0 | | ローカルLLM 8B | 5.0 |
| Docker | 5.0 | | KVキャッシュ | 4.0 |
| エディタ・ブラウザ | 4.0 | | 埋め込みモデル | 1.5 |
| 予備 | 4.0 | | バッチ作業域 | 3.5 |
| | | | 予備 | 5.0 |

**運用ルール**

- ローカル8Bは常駐させず、業務ジョブが入ったらロード、アイドルでアンロード
- 検出パイプライン（1GB）は常駐。**マスキングの主力をLLMではなくルール＋CPU NERに置いたのは、8Bが落ちていても送出ゲートを機能させるため**
- 重いビルド（Next.jsのフルビルド、テストスイート）は早めにCIへ逃がす。セキュリティのためだけでなくメモリのため
- Dockerは使う分だけ起動。ブラウザは平気で4GB超えるので実測すること
- 開発と業務を常時両立させようとしない

## 3. ソフトウェア構成

| レイヤー | 採用 | 備考 |
|---|---|---|
| 推論エンジン | **MLX (mlx-lm)** ＋ llama.cpp | Apple Siliconネイティブ。Ollamaから始めてもよい。**vLLMは実質NVIDIA前提で使えない** |
| メインモデル | 8B級・4bit（オンデマンド） | 重み約4.5GB、25〜30 tok/s程度。日本語は自社文書で選定する |
| 予備モデル | 14B級4bit / 30B級MoE | 他を止めて回すバッチ専用 |
| 埋め込み・再ランク | 多言語埋め込み（日本語対応必須） | 再ランカでコンテキストを短縮するとprefillの遅さが緩和される |
| モデルルータ | **LiteLLM** | ローカルと商用APIを同じOpenAI互換I/Fで。仮想キーで区分・予算を分離 |
| エージェント実行 | **LangGraph** | Postgres checkpointerで中断・再開。MCPクライアントも兼務（独立したMCPゲートウェイは立てない） |
| MCPサーバ | **FastMCP** | ネイティブPythonプロセスとして常駐 |
| データ | **PostgreSQL + pgvector** | Homebrewでネイティブ起動。ベクトル・状態・マスク対応表・監査ログを集約。FileVault必須 |
| 可観測性 | **Phoenix** | OTel互換で軽量。Langfuseは ClickHouse依存で32GBに載らない |
| アクセス制御 | **Tailscale** | ポート開放不要。動的IP・CGNATでも可。Keycloakは重すぎる |
| シークレット | macOS Keychain ＋ SOPS/age | 1台構成でOpenBaoを立てる意味は薄い |
| プロセス管理 | **launchd** | GUIログインやDocker Desktopに依存させない（自動復帰しないため） |
| コンテナ | OrbStack / Colima | Docker DesktopはLinux VMのオーバーヘッドで数GB食う |

**載せないもと判断したもの**: Dify、Keycloak、Langfuse自己ホスト、Temporal、ClickHouse、MinIO、Docker Desktop、OpenBao、独立MCPゲートウェイ。すべて32GBに収まらないか、1台構成では過剰。

## 4. 送出ゲート — 機密データの扱い

設計の中心。「重い推論は外に出す」と「顧客情報は外に出さない」を両立させる唯一の場所。

### データ区分

| 区分 | 対象 | 処理先 | 保証の方法 |
|---|---|---|---|
| **A** | 顧客個人情報の生データ、口座情報、未公開の財務数値 | ローカル8Bのみ（オンデマンド） | 専用の仮想キーに**外部モデルを一切紐付けない**。構造で塞ぐ |
| **B** | 契約書、社内文書、議事録、顧客名を含むコード | ローカルでマスク → 商用API → 復元 | 送出内容（マスク後の全文）を必ず記録 |
| **C** | 公開前提のコンテンツ、一般的なコード、調査、翻訳 | そのまま商用API | 予算上限のみ。**開発ゾーンの大半はここ** |

### 区分Bの処理手順

1. **決定的な検出** — 正規表現でメール・電話・口座番号・金額・住所を抽出（常駐層）
2. **固有表現の検出** — 日本語NER（GiNZA等のCPUライブラリ）で人名・企業名。8Bが落ちていても動く
3. **プレースホルダ置換** — `<PERSON_01>` の形に置換。対応表はリクエスト単位でPostgreSQLへ。**対応表はMac miniから出ない**
4. **送出前の再スキャン** — 既知パターンが残っていれば送出中止、人間に回す
5. **外部API呼び出しと記録** — マスク済みのみ送出。送出内容をそのまま監査ログへ
6. **復元** — プレースホルダを戻す。未知のプレースホルダは異常として扱う

### 限界

**マスキングは100%ではない。** 文脈から個人が特定できる記述（「先週退職した経理担当」等）はパターンで検出できない。だから区分Aを設けて、本当に出せないものは経路そのものを断つ。マスキングは区分Bのための安全策であって区分Aの代替ではない。

## 5. 開発と業務を1台の中で分ける

macOSの別ユーザーアカウントによる分離が最も強いが、常駐が二重になり32GBでは非現実的。以下の権限分離を採る。

| 層 | 分け方 | 防げること |
|---|---|---|
| ファイル | 業務データはAPFS暗号化ボリューム。MCPのファイルサーバを2本立ててルート固定 | 開発エージェントがファイル検索で顧客情報を拾う事故 |
| データベース | 同一インスタンスでよいが業務DB/開発DBとロールを分ける | RAG検索やSQL実行ツールが業務データに届く事故 |
| ツール（MCP） | 業務用/開発用を別プロセス・別資格情報で起動 | 開発エージェントが会計システムや顧客DBを呼ぶこと |
| モデル | LiteLLM仮想キーを3本（業務A用=ローカル専用 / 業務B用 / 開発用=外部のみ） | 区分Aの外部送信。開発の暴走で業務側の予算を使い切ること |
| 本番権限 | AWSプロファイルを読取専用（エージェント用）とデプロイ用（人間・CI用）に分離 | エージェントが本番を書き換えること |
| 記録 | Phoenixトレースをゾーン別プロジェクトに。業務側は暗号化ボリューム上に | トレースDB経由の情報漏れ（見落としやすい） |

**コンテンツ制作の扱い** — 記事・画像・資料は開発ゾーン側（公開前提で機密度が低い）。ただし顧客名や実績を含む事例記事は業務ゾーン扱いとし、公開可否の確認を挟む。

## 6. 本番へのデプロイと権限（段階的CI移行）

現在は MacBook から直接デプロイ。Mac miniに移すと、自律的に動くエージェントが常駐するマシンに本番権限が乗る。

1. **今すぐ — AWSプロファイルを分ける**。エージェント参照分は読み取り専用に限定し、デプロイ用をエージェントの環境変数・設定ファイルから完全に外す。**この1手で最悪ケースはほぼ塞げる**
2. **リポジトリを整える** — デプロイ手順をスクリプト化。この時点ではまだMac miniから実行してよい
3. **CIでビルドまで走らせる** — デプロイは手動。ここでMac miniのメモリが楽になる
4. **CIにデプロイ権限を渡す** — OIDCでAWSロールを引き受ける。長期アクセスキーを発行しない。Mac miniからデプロイ用プロファイルを削除
5. **Mac miniを本番読み取り専用に** — ログ確認や状態取得のMCPは残してよいが書き込み系は持たせない

**移行完了までの暫定ルール**: デプロイをエージェントに実行させない。コマンド組み立てまでは任せてよいが実行は人間。人間の注意力に頼らず、**エージェントの実行環境にデプロイ用資格情報を置かない**形にする。

## 7. モデルの使い分け

| ゾーン | 仕事 | 処理先 |
|---|---|---|
| 開発 | コード生成・設計・リファクタリング | 商用API（8Bとの品質差が最大。節約するとレビュー工数で損） |
| 開発 | コンテンツの下書き・推敲・翻訳 | 商用API |
| 開発 | ログ解析・エラー分類 | ローカル可（本番ログに顧客情報が混ざるなら区分B扱い） |
| 業務 | 個人情報の検出・マスキング | ルール＋NER常駐 |
| 業務 | 請求・契約書の項目抽出 | ローカル8B（区分A・オンデマンド） |
| 業務 | 社内文書の埋め込み・検索 | ローカル固定 |
| 業務 | マスク後の長文要約・分析 | 商用API（区分B・ゲート経由） |
| 業務 | 大量文書のバッチ処理 | ローカル・夜間 |

**ローカル推論は直列化する** — 帯域律速のため並列化してもスループットは増えずレイテンシだけ悪化。Redisキューで1本ずつ流す。

## 8. 商用LLM API の契約

**本命 = Amazon Bedrock**。既存AWS請求に合流、IAMで権限制御、CloudTrailに呼び出し履歴。東京リージョン＋`jp.` 推論プロファイルで処理を国内に閉じられる（最新世代モデルは現状Globalのみ）。比較・保険として直販（Anthropic または OpenAI）を1本持つ。

- 各社ともAPIデータはモデル学習に使われない。標準保持は30日前後。**ZDRは営業承認制**だが、区分Aを送らない設計なので必須ではない
- 単価の目安（USD/100万トークン、2026年9月）: 主力帯 入力$2 / 出力$10〜12、小型帯 入力$0.20〜1 / 出力$1.20〜5
- バッチは各社50%引き、キャッシュ読みは入力の10%
- 国内完結が契約要件になった場合の逃げ道: さくらのAI Engine、PLaMo（円建て・入力¥60 / 出力¥250 per 1M）
- **アグリゲータ（OpenRouter等）は社内機密には使わない** — データ取扱いが背後の各プロバイダ依存で経路の説明がつかない。集約は自社側のLiteLLMで行う
- 予算上限は必ずLiteLLM側の仮想キーごとに設定する（プロバイダ側の設定に頼らない）

## 10. 自宅で常時稼働させる

- `pmset` でスリープ無効化、**停電復帰後の自動起動を有効に**。サービスは launchd で起動
- **FileVault を有効にし、業務データはさらに暗号化ボリュームへ**。物理的な盗難が現実的な脅威になる
- **ポート開放はしない**。外部アクセスはTailscaleのみ。Webhook受信が必要ならEC2で受けてTailscale経由でMac miniへ
- 家庭内の他端末とネットワークを分ける（VLANまたは専用SSID）
- **監視はEC2側から** — 自分自身は自分の停止を通知できない
- **バックアップは3系統** — 業務DBの日次ダンプ（暗号化してS3）／開発リポジトリ（Gitが正）／設定一式（SOPSで暗号化してgit）。**復元手順を一度実際に試すまで「バックアップがある」と言わない**
- **1台故障で開発も業務も止まる**。本番AWSは動き続けるので事業は継続するが、作業はMacBookの最小環境に落ちる

## 11. 導入順序

| | 期間 | 内容 | 完了判定 |
|---|---|---|---|
| **STEP 1** | 1週 | FileVault・暗号化ボリューム、pmset・launchd・Tailscale、**AWSプロファイル分離**、PostgreSQL（業務DB/開発DB分離） | 再起動して人が触らずに全部戻る |
| **STEP 2** | 2週 | MacBookからMac miniへ作業移行、LiteLLM＋Bedrock、Phoenixでキャッシュ率実測、CIでビルド | メモリ実測が配分の範囲に収まる |
| **STEP 3** | 3〜4週 | 正規表現＋GiNZA常駐化、プレースホルダ置換と復元、8Bのオンデマンド起動、**自社の実文書で取りこぼし検証** | 区分Bを外に出せる根拠が説明できる |
| **STEP 4** | 4〜6週 | 業務を1つ自動化、社内文書RAG、CIにデプロイ権限移管 | Mac miniに本番の書き込み権限が残っていない |

## 12. 意図的にやらないこと

- **マルチエージェントの複雑な協調** — 失敗の原因が追えずトークンも食う。単一エージェント＋明示的なワークフロー分岐で始める
- **専用ベクトルDBの先行導入** — pgvectorで足りるうちは運用対象を増やさない
- **ファインチューニング** — 「精度が出ない」のほぼ全てはプロンプトと検索精度の問題
- **無人での外部発信** — メール送信・顧客への返信・支払い処理は人間承認を挟む
- **デプロイのエージェント実行** — 上記6節のとおり

---

## 13. 未決事項

- **顧客との契約にデータ保管場所・再委託の条項があるか** — 自宅設置で最初に潰すべき論点。技術より先
- **区分Aの具体的な定義** — 広すぎるとローカル8Bの品質で全部やる羽目になり、狭すぎると意味がない。実際の書類を数点見ながら決める
- 最初に自動化する業務の選定（毎週2時間以上・手順が言語化できる・間違えても人が気づける）
- 本番AWSの構成をコード化（Terraform等）するか — CI移行のついでに検討する価値あり
- Mac mini の購入有無 — 開発ホストを兼ねる以上、**M5 Pro / 64GB**（帯域307GB/s、メモリ2倍）の検討価値は上がっている

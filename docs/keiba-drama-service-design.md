# サービス設計書 — 競馬ドラマ発掘エージェント（仮称: HOOFPRINTS）rev.1

2026-09-09 / 位置づけ: AIエージェントプラットフォーム rev.3 の**最初の実サービス**。
プラットフォーム設計（`claude/platform-architecture.md`）の検証を兼ねる。

---

## 1. サービスの定義

競馬の結果はレースの一瞬に見えるが、その一頭が生まれるまでには生産牧場の交配の判断があり、
育成の年月があり、馬主の出資判断があり、調教師の管理方針があり、騎手の騎乗依頼の経緯がある。
このサービスは**その背景を掘り起こし、事実に出典を付けた読み物としてWebで公開する**。

読者に提供する価値は「当たる情報」ではなく「応援する理由」。

### やらないことを先に決める

| やらない | 理由 |
|---|---|
| **予想・買い目の提供** | サービスの立場（賭け事を超えた応援）と矛盾する。同時に、的中率という検証可能な約束を負わずに済む |
| **予想サイトのアフィリエイト** | 上と同じ理由。収益源として真っ先に思いつくが、ここを踏むとサービスの信頼が一度で消える |
| **オッズ・馬券の販売情報への誘導** | 各配信プラットフォームのギャンブル関連規約に触れるリスクを構造的に避ける |
| **競走馬データそのものの提供** | データベース提供は権利処理の次元が変わる（7節）。あくまで読み物 |

この4つを外すことが、コンプライアンス設計の8割を占める。**制約ではなく、設計上の最大の単純化。**

## 2. プラットフォーム検証としての位置づけ

このサービスを最初の題材に選ぶ理由は、コンテンツ事業として有望だからではなく、
**プラットフォームの主要な機構を一通り、しかも低リスクで通せるから**である。

| プラットフォームの機構 | このサービスでの検証内容 |
|---|---|
| **LangGraph + Postgres checkpointer** | 「人間承認待ち」で数日中断し、再開する。中断・再開の実運用テストとして理想的 |
| **LiteLLM 仮想キー** | 記事生成用キーに月額上限を設定。1本あたりコストを実測する |
| **送出ゲート 区分C** | 記事の下書き・推敲・翻訳。開発ゾーンの大半がここという想定の実証 |
| **送出ゲート 区分B** | 取材メモ（未公開の個人の発言・連絡先）のマスク→外部→復元。**実データでマスキングの取りこぼしを検証できる、機密度の低い題材** |
| **送出ゲート 区分A** | 収益・支払いの記録は業務ゾーン。ローカル固定 |
| **PostgreSQL + pgvector** | 出典・主張・記事の格納と、既出テーマの重複検出 |
| **Phoenix** | プロンプトキャッシュのヒット率実測（月額を左右する最大の変数） |
| **CI → 本番AWS** | 静的サイトのビルド・デプロイをCIに載せる。Mac miniから本番書き込み権限を外す実地検証 |
| **人間承認ゲート** | 「無人での外部発信をしない」原則の実装形を確定させる |
| **ローカル8B** | 使いどころが少ない。ログ分類と重複判定程度。**このサービスは「開発ゾーンはほぼ外部API」という設計判断の裏取りになる** |

顧客データを扱わないため、失敗しても損害が「恥ずかしい記事が公開される」で止まる。
機構の検証に使う最初の題材としてこの性質は重要。

## 3. コンテンツ設計 — 「ドラマ」を構造にする

### 3.1 アーキタイプ

ドラマを毎回ゼロから探すと、エージェントは「それらしい情動」を捏造する。
**型を先に定義し、事実がその型に当てはまるかを判定する**方式にする。

| 型 | 骨格 | 事実の出どころ |
|---|---|---|
| **血の物語** | 母・祖母の戦績と、その仔に託されたもの | 血統データ、過去のレース記録 |
| **牧場の物語** | 小規模生産者の初重賞、代替わり、地域の事情 | 生産者情報、地元紙、牧場サイト |
| **人の物語** | 調教師の定年最終年、騎手の復帰、厩務員の担当馬 | 報道、公式プロフィール、免許情報 |
| **馬主の物語** | 個人馬主の悲願、クラブ法人の出資者の視点 | 馬主情報、クラブの公開情報 |
| **再起** | 故障・長期休養からの復帰、未勝利脱出 | 出走間隔、競走中止記録、報道 |
| **別れ** | 引退、種牡馬入り、乗馬転向、功労馬 | 登録抹消情報、その後の報道 |
| **交差** | 過去に因縁のある人馬が同じレースで再会 | 過去の騎乗・対戦履歴の突合 |

型はスコアリングの単位でもある（4.1）。**型に当てはまらない馬は記事にしない。**
「全出走馬に物語がある」は正しいが、それを前提にすると全部が薄まる。

### 3.2 記事の中間表現

記事は最初からHTMLやMarkdownでは書かない。**Canonical Story という構造化データを作り、そこから各媒体の形へ変換する**（6節）。

```
Story {
  archetype:      血の物語 | 牧場の物語 | ...
  subject:        { horse_id, person_ids[], farm_id }
  hook:           1〜2文
  sections[]:     { heading, paragraphs[] }
  claims[]:       { claim_id, text, source_ids[], kind }   ← 全ての事実主張
  emotional[]:    { text, basis_claim_ids[] }              ← 情動的記述は必ず主張に紐付く
  sources[]:      { source_id, url, title, publisher, accessed_at, license_note }
  images[]:       { asset_id, credit, rights_status }
  disclosure:     { ai_assisted: true, reviewed_by, reviewed_at }
}
```

この構造の要点は **`emotional[]` が必ず `basis_claim_ids` を持つこと**。
出典のない主張に支えられない情動的記述は、検証ノードが機械的に落とせる。
これが「AIが感動を作りに行く」という最大の失敗モード（11節）への構造的な対策になる。

## 4. エージェント構成

単一の LangGraph グラフ。マルチエージェントの自律的協調はしない（プラットフォーム 12節の方針）。
ノードは明示的で、それぞれ入力と出力のスキーマが決まっている。

```
[1 Scout] → [2 Researcher] → [3 Fact Ledger] → [4 Outliner] → [5 Writer]
                   ↑                                              ↓
                   └──── 不足時に差し戻し ────────────  [6 Verifier]
                                                                  ↓
                                        [7 Human Gate] ←── interrupt（数日中断）
                                                ↓ 承認
                                        [8 Publisher] → 媒体アダプタ
```

| # | ノード | 処理先 | 内容 |
|---|---|---|---|
| 1 | **Scout** | ルール＋外部API（小型） | 直近・今後のレースから候補を抽出し、7つの型でスコアリング。**ここはLLMよりSQLの仕事が多い**（休養日数、母の戦績、生産者の重賞歴などは全部クエリ） |
| 2 | **Researcher** | 外部API（区分C）＋Web検索 | 候補について一次情報を収集。取得元URL・取得日時を必ず `sources` に記録。取材メモがある場合は**区分B**として送出ゲート経由 |
| 3 | **Fact Ledger** | 外部API（区分C） | 収集物から主張を抽出して `claims` に構造化。出典のない主張は破棄。既存DBと矛盾する主張はフラグ |
| 4 | **Outliner** | 外部API（区分C） | 型を確定し構成を組む。使える主張が閾値に満たなければ 2 へ差し戻し |
| 5 | **Writer** | 外部API（区分C・主力モデル） | 本文を生成。各段落が参照した claim_id を出力させる |
| 6 | **Verifier** | 機械チェック＋外部API（別プロンプト） | ①機械: 馬名・日付・着順・距離をDBと突合 ②LLM: 未出典の主張、出典と食い違う記述、根拠のない情動的記述を検出 |
| 7 | **Human Gate** | 人間 | LangGraph の interrupt で停止。Postgres checkpointer に状態が残る |
| 8 | **Publisher** | アダプタ | 承認された Story を各媒体形式へ変換し、自社サイトはCI経由、外部媒体はAPI投稿 |

**ローカル8Bの出番**: 重複判定の一次フィルタと実行ログの分類のみ。
記事本文の生成に8Bを使わないのは、プラットフォームの判断8「開発エージェントはローカルモデルを使わない」と同じ理由。

## 5. データモデル

PostgreSQL + pgvector。開発ゾーンのDB／ロールに置く（区分Cのため）。
**取材メモと掲載許諾のテーブルだけは業務ゾーン側**に置き、開発ゾーンからは参照キーのみを持つ。

| テーブル | 主な列 | 備考 |
|---|---|---|
| `horses` | 馬名、生年、性別、父、母、母父、生産者、馬主、調教師 | 公開情報から構築 |
| `people` | 種別（騎手/調教師/生産者/馬主/厩務員）、氏名、所属 | |
| `farms` | 牧場名、所在地、規模の目安 | 地方の小規模牧場が記事の核になる |
| `races` / `results` | レース、着順、タイム、騎手、人気 | |
| `sources` | URL、媒体、タイトル、取得日時、ライセンス注記、**embedding** | 一次情報の台帳 |
| `claims` | 主張テキスト、対象、source_ids、種別、検証状態 | **中核テーブル** |
| `stories` | 型、対象、状態、Canonical Story（JSONB）、**embedding** | |
| `story_claims` | story ↔ claim | |
| `media_targets` | 媒体名、文字数上限、AI開示の要否、外部リンク可否、投稿方式 | **規約差はコードでなくデータで持つ** |
| `publications` | story、媒体、公開URL、公開日時、canonical指定 | |
| `review_events` | 承認/差し戻し/破棄、理由、担当 | プロンプト改善の材料。捨てない |
| `consents`（業務ゾーン） | 取材対象、掲載許諾の有無・範囲・日付 | 区分B/Aの境界 |

`stories.embedding` と `sources.embedding` により「この切り口は3ヶ月前に書いた」を検出する。
コンテンツの同質化は、量産型メディアが最初に落ちる穴。

## 6. マルチ媒体配信の抽象化

収益源を1つの媒体に依存させないため、**Canonical Story を正本とし、媒体はすべて変換先**として扱う。

```
                    ┌─→ 自社SSG（正本・全文・出典つき）─ canonical URL
Canonical Story ────┼─→ note（抜粋＋導線 / 有料記事の実験）
                    ├─→ X・Threads（フック＋画像1枚）
                    ├─→ ニュースレター（週次まとめ）
                    └─→ 動画台本（Phase 4）
```

### 原則

1. **正本は必ず自社サイト**。他媒体には canonical を向けるか、抜粋＋導線に留める。
   プラットフォームのアルゴリズム変更やアカウント停止で資産が消える構造にしない。
2. **アダプタが持つのは「形式」だけではなく「規約」**。文字数、AI利用の開示要否、外部リンクの可否、
   自動投稿の可否は `media_targets` に持ち、変更があればデータを直す。コードに埋め込むと必ず古くなる。
3. **自動投稿は媒体ごとに個別判断**。自社サイトはCI経由で自動デプロイしてよい。
   外部SNS・note への投稿は承認後の明示的な操作にする（プラットフォーム 12節「無人での外部発信をしない」）。
4. **媒体を増やす前に1媒体で読まれることを確認する**。アダプタ機構は最初から作るが、
   稼働させるのは自社サイト＋note の2本から。

### AI生成コンテンツの扱い

2026年時点で各プラットフォームが収益化制限の対象としているのは
「反復的・大量生産的で付加価値のないコンテンツ」であり、AIの使用そのものではない。
このサービスの防御は次の3点で、いずれも既に設計に入っている。

- **一次情報の収集と出典の明示**（`sources` / `claims`）
- **人間による承認**（`review_events` に記録が残る）
- **型に当てはまらないものは書かない**（3.1）

AI利用の開示は媒体ごとの要否に従い、`disclosure` フィールドから自動で付与する。

## 7. 権利とコンプライアンス

**技術より先に潰すべき論点。** 調査結果を以下に記録する。

### 7.1 データの出どころ — 最重要の制約

**JRA-VAN Data Lab.（月額2,090円）は、個人のPCで動くソフトウェアのための契約であり、
そのデータを使って広告付き・課金のコンテンツをエンドユーザーに配信するのは「再配布（二次利用）」に当たる。**
その場合はJRAが提供する **JRADB の法人契約**が別途必要で、個人契約では対応できない（法人名・法人確認書類が必要、所定料金あり、窓口は JRA-VAN サポートデスク）。

したがって:

| フェーズ | データ方針 |
|---|---|
| **Phase 1〜3（収益ゼロ〜小）** | 公開情報（JRA公式サイト、報道、牧場・クラブの公開情報）から事実を組み立てる。**数値データは記事の根拠として使うが、データそのものを提供する形にはしない** |
| **Phase 4以降（収益化後）** | 記事本数と収益が JRADB の料金を正当化する水準に達した時点で法人契約を検討。**それまで JRA-VAN のデータを事業に組み込まない** |

無料のスクレイピングで代替する誘惑があるが、各サイトの規約と負荷の問題があり、
**事業として続けるつもりなら最初から踏まない**。Phase 1 の記事本数（週2本）なら公開情報の手作業＋エージェント収集で足りる。

### 7.2 馬名・人名

競走馬の名称については、最高裁 平成16年2月13日判決（ギャロップレーサー事件）が
**「物のパブリシティ権」を否定**しており、馬名を記事で使うこと自体は権利侵害にならない。
ただし個別に商標登録されている名称・ロゴ、および馬主団体等の名称の使用は別問題。

存命の人物（騎手・調教師・生産者）については名誉毀損・プライバシーの一般的な規律に従う。
**公表された事実の記述は可、私的な事情の推測は不可**を編集方針として明文化する。

### 7.3 画像 — 最大の未解決リスク

JRA・報道機関のレース写真は使えない。選択肢は3つで、**現時点で決めきれていない（12節）**。

| 案 | 可否 | 課題 |
|---|---|---|
| 自前撮影 | ◯ | 現地取材のコスト。ただし牧場取材とセットなら価値が高い |
| ストック/ライセンス購入 | ◯ | 「その馬」の写真は基本的に存在しない |
| 生成画像＋タイポグラフィ | ◯ | **実在馬の写実的な再現は避け**、抽象ビジュアル・図解・血統図で構成する |

Phase 1 の現実解は3案（血統図・戦績のデータビジュアル・抽象的なキービジュアル）。
写真がなくても成立する記事設計にしておくこと自体が要件。

### 7.4 取材メモの扱い

牧場や関係者への取材メモは、未公開の発言・連絡先・私的な事情を含むため **区分B**。
要約や構成にLLMを使う際は送出ゲート経由（マスク→外部→復元）。
掲載許諾は `consents`（業務ゾーン）で管理し、許諾のない発言は Story に入らないよう
Human Gate のチェック項目に入れる。

## 8. 収益モデル

目標は「このサービスの運用費を賄う」。プラットフォーム全体の月額 ¥31,000〜90,000 のうち、
本サービスの取り分を **月 ¥15,000〜30,000** と置く（記事生成のAPI費＋ドメイン＋ホスティング＋データ費）。

### 8.1 コスト側

| 項目 | 月額の目安 |
|---|---|
| 記事生成API（区分C・週2〜10本） | ¥2,000〜10,000（1本 ¥50〜150 を目標に実測） |
| ホスティング（S3+CloudFront・SSG） | ¥500〜2,000 |
| ドメイン | ¥100〜200 |
| 画像・素材 | ¥0〜10,000（方針未定） |
| データ（Phase 4以降） | JRADB 法人契約: 要見積 |

**最大のコストはAPIではなく、承認と取材の人時間。** Phoenix で1本あたりのトークンコストを実測し、
同時に承認にかかった時間も `review_events` に記録して、両方を可視化する。

### 8.2 収益側 — 段階と判断基準

| 段階 | 手段 | 現実的な水準 | 判断 |
|---|---|---|---|
| **A** | 自社サイト広告 | 数万PVで月数千円。**単独では届かない** | 置くが期待しない |
| **B** | note 有料記事・メンバーシップ | 100人 × 月500円 = 月5万円。**ドラマ系コンテンツと相性が良い** | 本命の第一候補 |
| **C** | アフィリエイト（一口馬主クラブ、書籍、牧場のふるさと納税、競馬関連物販） | 月数千〜2万円 | Bの補助。予想サイト系は扱わない |
| **D** | 牧場・クラブからの記事制作受託 | 1本 数万円。**単価が最も高い** | メディア自体がポートフォリオになる。**実は本命** |

**判断基準を先に決めておく:**

- 6ヶ月で B が月1万円に届かなければ、記事の型か対象（中央→地方など）を変える
- 12ヶ月で A+B+C の合計が運用費を割るなら、D（受託）に軸足を移し、メディアは営業資産と位置づける
- **どの段階でも「予想を出せば早い」という誘惑には乗らない**。乗った時点で別のサービスになる

## 9. 実装フェーズ — プラットフォームのSTEPと噛み合わせる

| | 内容 | プラットフォーム側の対応 | 完了判定 |
|---|---|---|---|
| **Phase 0**（2週） | **エージェントを作らず、人間が記事を3本書く**。型・文体・構成・出典の粒度を確定 | — | Canonical Story のスキーマが3本の実物から決まる |
| **Phase 1**（3週） | DB構築、Scout・Researcher・Fact Ledger を実装。執筆は人間 | STEP 1〜2（PostgreSQL分離、LiteLLM+Bedrock、Phoenix） | 候補5件に対し、使える主張が出典つきで集まる |
| **Phase 2**（4週） | Outliner・Writer・Verifier、承認UI、自社SSG、CIビルド＋デプロイ | STEP 2 の完了判定（メモリ実測、CIビルド） | 承認を経て1本が本番に公開される。Mac miniにデプロイ権限がない |
| **Phase 3**（4週） | 取材メモの区分B処理、note アダプタ、重複検出 | STEP 3（送出ゲートの実文書検証） | 取材メモをマスクして外部APIに通せる根拠が説明できる |
| **Phase 4**（継続） | launchd で定期実行、媒体追加、収益計測、JRADB要否判定 | STEP 4 | 週2本が承認待ちまで無人で到達する |

**Phase 0 を飛ばさないこと。** 型を持たない状態で自動化すると、
何が良い記事かを判定できないままプロンプトを弄り続けることになる。

## 10. 人間承認ゲートの設計

承認画面に出すもの（これが実質的な品質管理の全て）:

1. 記事本文（媒体ごとのプレビュー切り替え）
2. **出典のない主張のハイライト** — Verifier の出力
3. **機械チェック結果** — 馬名・日付・着順・距離のDB突合、不一致は赤
4. **根拠のない情動的記述** — `emotional[]` で `basis_claim_ids` が空のもの
5. 掲載許諾の状態（取材ベースの記事の場合）
6. 類似記事（embedding 検索の上位3件）

操作は3つ。**公開 / 修正指示して差し戻し / 破棄**。
差し戻しと破棄には理由を必須入力にし、`review_events` に蓄積する。
これがプロンプト改善の唯一の一次データになる。

## 11. 失敗モードと対策

| 失敗モード | 深刻度 | 対策 |
|---|---|---|
| **事実誤認** | 高 — 競馬ファンは細部に厳しく、1回で信頼を失う | claims の出典必須 ＋ 数値のDB突合 ＋ 人間承認 |
| **感動の捏造** | 高 — LLMは「ドラマ」を作りに行く | `emotional[]` の根拠必須。型は選ぶものであって作るものではない |
| **当事者からのクレーム** | 中 | 掲載前連絡の基準を明文化、訂正窓口と手順を先に用意 |
| **コンテンツの同質化** | 中 — 量産型メディアが最初に落ちる穴 | embedding による既出検出、型の配分を意図的に散らす |
| **プラットフォーム依存** | 中 | 正本は自社。外部は抜粋＋導線 |
| **権利の見落とし**（特に画像） | 中 | 7.3 の方針を決めるまで写真を使わない |
| **承認がボトルネックになる** | 高 — 最も現実的な頓挫要因 | 週1回まとめて承認する運用にする。日次で承認を要求する設計にしない |
| **熱意の枯渇** | 高 | 8.2 の判断基準を先に決めてある。惰性で続けない／早すぎる撤退もしない |

## 12. 未決事項

- **画像の方針**（7.3）— Phase 0 の3本を書く過程で決める。最も早く決めるべき論点
- **サービス名・ドメイン** — `keiba.cetacea.jp` のサブドメインか独立ドメインか。
  受託（8.2 D）まで見るなら独立ドメインのほうが良い
- **地方競馬（NAR）を含めるか** — **ドラマの密度は地方のほうが高い可能性がある**。
  一方でデータ入手経路が中央と別系統になる。Phase 1 は中央に限定し、Phase 3 で判断
- **記事の頻度** — 週2本か週5本か。承認の人時間から逆算して決める。Phase 0 で実測
- **note と自社サイトのどちらを主軸にするか** — 6節では自社を正本としたが、
  読者の獲得は note のほうが速い。Phase 2 の実績を見て、正本の位置は変えずに導線設計だけ見直す
- **JRADB 法人契約の要否判定** — 判定の時期は Phase 4。それまでは公開情報のみ
- **既存 cetacea.jp（WordPress）との関係** — 別サイトとして立てる前提だが、
  WordPressを配信先アダプタの1つとして扱う選択肢もある
